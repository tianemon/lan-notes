## task-10 增量（Android 运行时 SQLite 库修复 + 多客户端增量转发）

> 背景：Evaluator 验收确认 9/9 任务 PASS，遗留两个问题——① Android APK 未打包 libsqlite3.so，运行时可能崩溃（手机端主场景）；② 主机不转发客户端间增量，3 台设备时 A 的变更无法实时到 B。

### 问题 1：Android SQLite 库修复（jniLibs 预编译库方案）

**调研结论**：

- `drift 2.34.3` 依赖 `sqlite3: ^3.4.0` → **sqlite3 2.x 方案不可行**（被 drift 版本约束排除），必须停留在 sqlite3 3.x native assets 体系
- sqlite3 3.x 默认 `source: sqlite3` 从 GitHub Releases 下载预编译库，本环境 GitHub 不可达；`source: source` 需全平台编译（Windows 依赖 MSVC 工具链，回归风险高）；`source: system` 在 Windows/macOS/iOS/Linux 可用，但 Android 无系统库可 dlopen
- 核对 sqlite3_flutter_libs 0.5.x 源码：其 Android 依赖实为 **`eu.simonbinder:sqlite3-native-library`**（sqlite3.dart 官方发布到 Maven Central 的 AAR，内含各 ABI 的 libsqlite3.so），并非 task 描述的 org.sqlite:sqlite3-android；腾讯云 Maven 镜像（mirrors.cloud.tencent.com）可达

**实施方案（零依赖改动、Windows 零回归）**：

1. 保持 `sqlite3 3.5.1 + sqlite3_flutter_libs 0.6.0+eol` 与 hooks `source: system`（Windows 继续用系统 winsqlite3，构建路径完全不变）
2. 从 Maven 镜像下载 `eu.simonbinder:sqlite3-native-library:3.52.0` AAR，解出 `jni/{abi}/libsqlite3.so`（arm64-v8a / armeabi-v7a / x86_64），放入 `android/app/src/main/jniLibs/{abi}/`（预编译库随工程版本控制，构建完全离线）
3. Android 运行时：sqlite3 3.x 的 `DynamicLoadingSystem('libsqlite3.so')` 走 Android 应用 linker 命名空间 dlopen，命中 APK 内打包的 libsqlite3.so（Android 标准机制，与系统其它库同名冲突风险低——系统库名为 libsqlite.so）

**验证结果**：

- `flutter build apk --debug` 成功；`unzip -l app-debug.apk` 确认 3 个 ABI 均含 `lib/…/libsqlite3.so`（arm64-v8a/armeabi-v7a/x86_64，各 ~1.5MB）
- `flutter build windows` 成功（无回归，系统库路径未动）

**权衡与遗留**：

- 未采用 sqlite3 2.x（drift 约束不兼容）；未采用 `source: source` 编译（全平台编译、Windows 工具链风险）；jniLibs 预编译库方案改动面最小，Windows 构建路径零变化
- AAR 内置 SQLite 3.52.0（sqlite3 3.5.1 自带 3.53.4，API 向后兼容，绑定符号 3.52.0 均具备）；x86（32 位）ABI 未提供（现代设备/模拟器均为 arm64-v8a/x86_64/armeabi-v7a）
- 本机无 Android 设备/模拟器，**真机运行时验证仍待补**（dlopen 命中 jniLibs 为 Android 标准机制，理论成立）；如需更换版本，从 Maven 镜像重新拉取 AAR 替换 jniLibs 即可

### 问题 2：多客户端增量转发（fan-out）

**修复**：

- `SyncServer` 新增 `broadcastExcept(message, except)`：广播给除指定连接外的所有已连接客户端

## task-11 增量（发现层修复：列表去重 + Android 多播锁）

> 背景：真机实测反馈两个问题——① 发现列表出现重复设备（同一设备被列出两条）；② 手机端发现/连接慢（几分钟，偶尔秒连）。根因：`_discoverOnce` 无去重（同一实例多条 A 记录/PTR 缓存叠加生成多条）+ Android WiFi 省电时内核过滤多播包（需 MulticastLock）。

### 问题 1：发现列表去重（discovery_service.dart）

**修复**：

- `_discoverOnce` 结果按实例名（instanceName）去重：新增 `_deduplicateByInstance`，同一实例分组后由 `_pickBestDevice` 选最优可连接条目
- 地址优先级：回环（127.x）< 链路本地（169.254.x）< 真实网卡地址（其余）；分值相同保持解析顺序（multicast_dns 缓存顺序稳定，输出可预期）
- 覆盖两类重复来源：① 同一实例发布多条 A 记录（多网卡/多 IP，见 `_MDnsResponder._addressAnswers`）；② multicast_dns 缓存未过期与新响应叠加，同一实例 PTR 记录被重复解析
- 每轮仍输出完整列表（非增量），由 `_pollOnce` 广播，去重后每个实例恰一条

**说明**：发布端 `_localIPv4Addresses` 已排除虚拟网卡（task-9 修复），主路径 A 记录均为真实网卡；发现端仅有 IP 无网卡名，故虚拟网卡判断退化为排除链路本地/回环（记录为遗留）。

### 问题 2：Android 多播锁（MulticastLock）

## task-15 增量（修复验收问题：fan-out 回声风暴 + 同名设备去重 + 健壮性加固）

> 背景：Evaluator 验收发现 1 个 HIGH（三设备全互联 fan-out 无限中继回声循环）与
> 1 个 MEDIUM（发现去重按 instanceName 合并同名设备）及若干 LOW 问题。

### 【HIGH】fan-out 回声风暴修复（lib/app/sync/sync_service.dart + note_repository.dart）

- **根因**：`_onNoteUpsert` / `_onNoteDelete` 无条件 fan-out——全互联 mesh（A↔B /
  A↔C / B↔C）下，A 的变更直接推给 B/C，B/C 合并后各自转发给对方，对端收到的是
  **未变更**（重复）消息，但旧逻辑仍继续转发：A 的变更经 B→C→A→B…无限循环。
  联调实测（临时移除门控复现）：1.5s 内单条笔记被每台设备处理 **2586+ 次**且持续增长
- **修复**：`mergeRemoteNote` / `mergeRemoteDelete` 改为返回**是否实际变更本地**
  （bool：写库为 true；未采用远端/内容版本一致/本地已删/乱序过期为 false）；
  `_onNoteUpsert` / `_onNoteDelete` **仅当合并实际变更本地时才 `_fanOutToOthers`**，
  未变更消息直接丢弃。修复后每条笔记在 mesh 中至多被每台设备处理 2 次
  （1 次直接推送 + 1 次对端 fan-out，第二次为未变更回声被丢弃），消息链收敛
- **验证**：verify_sync.dart 新增**场景九（全互联 mesh 消息收敛，8 项断言）**——
  用计数仓库（`_CountingRepository`）统计每台设备对每条笔记的 merge* 处理次数，
  断言每台 ≤ 2 次（upsert 与 delete 均验证）且观察窗口内计数**停止增长**；
  临时移除门控复现风暴时计数爆炸（2586→4394），修复后稳定 [0,2,2]

## task-24 增量（UDP 广播发现改造：mDNS → UDP，完整实现）

> 背景：发现层从 mDNS 改为 UDP 广播（参考 Syncthing lib/discover/local.go 周期广播 +
> LocalSend multicast_discovery.dart 上线三连发/回播），连接/同步层零改动。
> 旧版（mDNS）与新版（UDP）互不可见，所有设备需升级到新版（README 已加升级说明）。

### 实现（lib/app/sync/discovery_service.dart 完整重写）

- **协议**：UTF-8 JSON 通告 `{v:1, deviceId, name, port, ts}`，UDP 广播端口 58888
  （与 WebSocket TCP 58888 同号，UDP/TCP 独立不冲突）；对端 IP 取数据报源地址。
- **发送**：逐网卡计算子网广播地址（dart:io 不暴露 netmask，按私有网段惯例推导
  `10/8`、`172.16/12`、`192.168/24`，其余按 /24）+ `255.255.255.255` 兜底；
  过滤虚拟/断开网卡（utun/awdl/bridge/anpi/Hyper-V 等），排除 loopback/链路本地；
  发送失败 try-catch 容忍不影响后续。
- **时序**：publish/startDiscovery 时三连发（默认 100ms/500ms/2s，延迟序列可注入）+
  周期通告（默认 30s，可配置）；收到**新 deviceId** 通告立即回播一次自己的通告，
  记录最近回播 deviceId+时间限频（默认 30s 窗口，防已收到风暴）。
- **接收**：绑定 UDP 58888（reuseAddress；macOS/Linux 加 reusePort 同机多实例共存，
  Windows 无 SO_REUSEPORT 降级仅 reuseAddress——Windows 下 SO_REUSEADDR 广播投递给
  全部同端口 socket）；JSON 容错（坏包忽略）；按 deviceId 去重；isSelf = 通告
  deviceId == 本机 deviceId；按 deviceId 记录 lastSeen，超过默认 90s 无通告定时
  清理离线移除（deviceExpiry 可注入短值验证）。
- **API 完全保持**：publish({deviceName, port, deviceId}) / unpublish / startDiscovery /
  stopDiscovery / devices 流 / isPublishing / isDiscovering / dispose +
  DiscoveredDevice 字段（instanceName 以 deviceId 占位）——SyncService 与同步页
  UI 调用点**零改动**。
- **身份注入**：deviceId/deviceName 经 publish 传入（SyncService 从 DeviceIdentityStore
  读取）；构造参数可注入确定性身份（verify_sync.dart 场景十三/十四）。
