# 局域网笔记 — 技术架构

## 1. 技术选型

| 层 | 选型 | 版本 | 理由 |
|------|------|------|------|
| 跨平台框架 | Flutter | 3.38.5 stable | 一套代码覆盖 iOS/Android/Windows/macOS，桌面端与移动端均为官方稳定支持 |
| 本地存储 | drift + sqlite3_flutter_libs | 最新 | 类型安全的 SQLite ORM，支持流式查询（Stream），官方维护 |
| 状态管理 | flutter_riverpod | 最新 | 编译期安全、易测试、依赖注入清晰，社区主流 |
| 路由 | go_router | 最新 | Flutter 官方推荐声明式路由，支持深链与统一导航配置 |
| 设备发现 | UDP 广播（自研，task-24） | 最新 | UDP 广播通告 JSON（端口 58888），参考 Syncthing 周期广播 + LocalSend 上线三连发/回播；无需 mDNS 依赖与 MulticastLock |
| 同步通道 | web_socket_channel | 最新 | WebSocket 双向实时通信，Flutter 官方包 |
| ID 生成 | uuid | 最新 | 笔记全局唯一 ID（跨设备合并前提） |

**选型依据**：所有依赖均为 Flutter/Dart 官方或社区成熟维护项目；局域网同步完全本地实现，无任何云服务依赖，符合「免费 + 本地部署」约束。

## 2. 总体架构（分层）

```
┌─────────────────────────────────────────────┐
│ UI 层：Pages / Widgets（Home / Editor / Sync）│
└──────────────────┬──────────────────────────┘
┌──────────────────▼──────────────────────────┐
│ 状态层：Riverpod Providers（笔记/同步状态）     │
└──────────────────┬──────────────────────────┘
┌──────────────────▼──────────────────────────┐
│ 领域层：NoteRepository（统一读写入口）          │
│          SyncService（同步编排）               │
└──────┬───────────────────────┬──────────────┘
┌──────▼─────────┐   ┌─────────▼──────────────┐
│ 数据层：drift DAO │   │ 同步层：Discovery(UDP 广播) │
│ SQLite (notes 表) │   │   Connection(WebSocket)│
└────────────────┘   └────────────────────────┘
```

依赖方向自上而下，同步层与数据层互不直接依赖，通过 SyncService 桥接，保证**单机离线可用**（网络层崩溃不影响本地功能）。

## 3. 数据模型设计

### 3.1 notes 表（drift Table）

```dart
class Notes extends Table {
  TextColumn get id => text()();            // UUID，全局唯一（跨设备主键）
  TextColumn get title => text().withDefault(const Constant(''))();
  TextColumn get content => text().withDefault(const Constant(''))();
  IntColumn get createdAt => integer()();   // epoch ms
  IntColumn get updatedAt => integer()();   // epoch ms
  IntColumn get version => integer().withDefault(const Constant(0))(); // 同步版本号
  IntColumn get deletedAt => integer().nullable()(); // 软删除时间（null=正常，非 null=回收站）
  BoolColumn get isPinned => boolean().withDefault(const Constant(false))(); // 置顶（task-28）
  TextColumn get tags => text().withDefault(const Constant('[]'))(); // 标签 JSON 数组字符串（task-28）
  TextColumn get folderId => text().nullable()(); // 所属文件夹 id（task-32：null=未分类）
  @override
  Set<Column> get primaryKey => {id};
}
```

- **isPinned（task-28 置顶）**：BOOL 默认 false。置顶/取消经 `NoteRepository.setPinned` 变更（version+1 + updatedAt 刷新，随笔记 upsert 同步）；列表排序 **isPinned DESC → updatedAt DESC**（DAO 全量流与搜索流一致）；置顶笔记列表卡片标题右侧显示小图钉。
- **tags（task-28 标签）**：TEXT 默认 `'[]'`，存 JSON 数组字符串（如 `["工作","重要"]`）。经 `NoteRepository.setTags` 变更（version+1 随同步）；列表页顶部标签栏从全部笔记流聚合去重（不用单独表），点击筛选与搜索关键字并存；编辑页标签编辑（chip 输入，回车添加、chip 可删）。
- **content（task-29 富文本）**：TEXT 列类型不变，**自 schemaVersion 8 起存 delta JSON 字符串**——Quill Document 的 `toJson()` 序列化（如 `[{"insert":"你好\n"}]`，Quill 文档恒以换行结尾；空文档为 `[]`）。编辑页正文为 QuillEditor（所见即所得，flutter_quill v11），保存时 `jsonEncode(document.toDelta().toJson())`；列表摘要/字数经 `Note.plainTextOf`（data 层纯 Dart 实现，解析 delta 逐个 op 拼接 insert 字符串，embed 节点不计入）提取纯文本。**存量纯文本在 v7→v8 迁移时逐行转换**（`AppDatabase.contentToDeltaJson`：可解析为 List 视为已是 delta 原样保留，否则按纯文本补尾换行包一层 insert；空内容 → `[]`）。同步协议 v3 起 content 即 delta JSON，LWW 合并仍把 content 当不透明字符串处理（格式由协议版本保证）。**本地插图**（见 3.4 节）：图片**绝对原图**（magic 判断扩展名）存应用支持目录 `attachments/<hash>.<ext>`，delta embed 节点引用相对路径；**协议 v4（task-30）起跨设备同步图片二进制**——接收方发现缺失附件自动请求分片传输、sha256 校验落盘、UI 自动刷新（见 3.4 节同步流程）。

- **folderId（task-32 文件夹归类）**：TEXT 可空，null=未分类。笔记移动 = folderId 置值 + version+1 + updatedAt 刷新，随 `note_upsert` 同步；列表筛选：选中文件夹仅显示 `folderId == 选中`，全部视图显示所有；folderId 指向已删除文件夹的笔记按未分类处理（只计入「全部」）。

### 3.1.1 folders 表（task-32 文件夹归类）

```dart
class Folders extends Table {
  TextColumn get id => text()();              // UUID，跨设备主键
  TextColumn get name => text()();
  IntColumn get createdAt => integer()();     // epoch ms
  IntColumn get updatedAt => integer()();     // epoch ms
  IntColumn get version => integer().withDefault(const Constant(0))(); // LWW 版本号
  IntColumn get deletedAt => integer().nullable()(); // 软删除标记（null=正常）
  BoolColumn get isPinned => boolean().withDefault(const Constant(false))(); // 置顶
  IntColumn get sortOrder => integer().withDefault(const Constant(0))(); // 手动排序键
  TextColumn get origin => text().nullable()(); // 最后修改者（同 Notes.origin）
  @override
  Set<Column> get primaryKey => {id};
}
```

- **字段体系与 notes 完全同构**：LWW 合并框架复用（version 大者胜 → 操作时间 → 删除优先），无墓碑（文件夹删除 = 软删除不可恢复，无回收站；复活由 LWW 版本裁决，与笔记软删除语义一致）。
- **排序**：抽屉排序 `isPinned DESC → sortOrder ASC`（置顶区在前、区内按拖拽顺序）；拖拽排序后 `sortOrder` 归一化为 0..n-1（`FolderRepository.reorder`，逐条 version+1 随 folder_upsert 同步）；跨区移动（置顶↔普通）走菜单「置顶/取消置顶」，操作后自动归一化。
- **删除文件夹二选一**：①「笔记移到全部」= 文件夹软删除 + 内全部活跃笔记 folderId 置 null（note_upsert 逐条）；②「同时删除笔记」= 文件夹软删除 + 内全部活跃笔记软删除进回收站。两者均随同步传到对端。

### 3.2 索引

- `updatedAt` 索引：列表按更新时间倒序
- `version` 不建索引（量小，同步全表扫描可接受）

### 3.3 同步冲突模型（LWW — Last Write Wins，v3 修订）

- 每条笔记维护 `version`（单调递增的整数版本号）+ `updatedAt`（epoch ms 时间戳）+ `deletedAt`（null=正常，非 null=回收站）
- **合并规则**（对所有操作统一）：① version 大者胜；② version 相等时比较操作时间（`updatedAt` vs `deletedAt`），新者胜；③ 时间也相等时**删除优先**（防复活兜底）
- **删除策略（v3 修订：硬删除+广播 → 回收站+墓碑）**：
  - 删除 = 软删除（`deletedAt` 置时间 + version+1），内容保留在回收站，跨设备同步
  - 恢复 = 清除 `deletedAt` + version+1，同步恢复
  - 清空（单条/全部）= 物理删除 + 写**墓碑**（id + version + 时间），同步 `note_delete`
  - **墓碑防复活**：全量同步携带墓碑列表，离线设备带回的旧数据按 version/时间比较被墓碑拦截；墓碑永不清除（个人量级可忽略）
  - **UI 落地（task-22）**：列表页/编辑页删除入口统一改为「移到回收站」（软删除）；新增回收站页（`/trash`）提供恢复 / 清空单条 / 清空全部，见第 4/5 节
  - **旧版设备兼容（task-21/23）**：旧对端不识别 `deletedAt`/墓碑——旧设备删除仍为硬删除广播（新端按 `note_delete` 处理 = 清空语义）；新端软删除/恢复旧设备不生效（旧端按普通 upsert 合并）。**删除功能需全员升级**：过渡期内删除同步受限，全部设备升级到 v3 后删除/恢复/清空全链路一致（README 已说明）

### 3.4 本地插图（task-29 富文本）

- **存储**：图片经 `AttachmentsStore`（lib/app/repository/attachments.dart）**绝对原图落盘**（不压缩、不缩放，任务迭代修订）——按文件头 magic 判断扩展名（jpg/png/gif/webp/bmp/heic），存入**应用支持目录** `attachments/<sha256前16位>.<ext>`（path_provider，内容寻址：同一图片去重；无法识别格式抛 `FormatException`）；delta 以 embed 节点引用相对路径：`{"insert":{"image":"attachments/<hash>.<ext>"}}`。
- **插入**：工具栏图片按钮 → `file_picker`（统一跨平台：macOS/Windows 文件选择、移动端相册/文件）→ 原图落盘 → 光标处 `BlockEmbed.image` 插入。
- **渲染**：编辑页 `QuillEditorConfig.embedBuilders` 提供 `image` 类型 embed builder——`AttachmentsStore.resolveFile` 解析相对路径 → `Image.file`；文件不存在（对端未同步/被清理）渲染占位图标不崩溃。
- **同步边界（task-30 修订：图片跨设备同步，协议 v4）**：delta 引用随笔记同步；**图片二进制经 file_request / file_chunk / file_complete 消息跨设备传输**（见 7.2 消息表与下方同步流程）。对端尚未收到图片时 embed builder 渲染占位；分片传输校验落盘成功后经就绪事件流自动刷新为图片。列表摘要 `Note.plainTextOf` 跳过 embed 节点（图片不计入文本）。

**图片跨设备同步流程（task-30，协议 v4）**：
```
A（有图）                      B（缺图）
  │  ① note_upsert/sync_data 携带 delta 引用    │
  │ ──────────────────────────────────────────→ │ ② 合并后解析 delta 引用（正则
  │                                             │    attachments/<16hex>.jpg）
  │  ③ file_request{fileId: hash}              │ ④ 本地 !exists(hash) 且不在请求
  │ ←────────────────────────────────────────── │    队列 → 入队（同 hash 去重）
  │  ⑤ 读本地文件分片（64KB → base64）           │
  │ ── file_chunk{chunkIndex, totalChunks} ──→ │ ⑥ 首个分片 createTemp(.part)，
  │        （逐片，WebSocket 保序）              │    后续 appendChunk（按 fileId
  │  ⑦ file_complete{fileId}                   │    串行化，顺序追加）
  │ ──────────────────────────────────────────→ │ ⑧ finalize：sha256 前 16 位 ==
  │                                             │    fileId → 重命名落盘 → 删临时
  │                                             │    → 就绪事件流通知 UI 刷新
  │                                             │    校验失败：删临时、移除请求，
  │                                             │    可重新请求
```
- **缺失检测**：`SyncService` 在 `_onNoteUpsert` 与 `_onSyncData` 合并后解析 delta content（正则 `attachments/([a-f0-9]{16})\.([a-z0-9]+)`，覆盖 quill image embed 值的多扩展名，原图方案修订），本地不存在且不在请求队列 → 向**来源会话**发 file_request（同 hash 去重）。
- **请求队列**：`Map<fileId, 状态>`，会话断开清空（重连后全量对齐重新检测）；请求超时（默认 30s，可注入）无响应 → 移除可重试；单文件上限 20MB——expectedSize 超限拒绝 / 接收累计超限中断（不重试）。
- **发送侧**：收到 file_request → 本地存在且（expectedSize 为 null 或与本地大小一致）→ 64KB 分片 base64 逐片发 file_chunk → file_complete；文件不存在/大小不符/超限 → 忽略（接收方超时放弃）。
- **接收侧**：分片按 fileId 串行写入 `.part` 临时文件（WebSocket 保序简单按序追加，乱序/重复分片中止传输）；file_complete 后 `AttachmentsStore.finalize` 校验 sha256 == fileId → 重命名落盘 → 删临时 → 就绪事件流（`AttachmentsStore.attachmentReady` 静态广播）通知 UI。
- **UI 刷新**：`_LocalImageEmbedBuilder` 渲染 `_AttachmentImage`（StatefulWidget）订阅就绪事件流——匹配本图 hash 的事件触发重新解析文件并重建 Image.file（占位 → 图片，无需手动刷新）；占位提示保留（对端无此图/尚未到达时）。
- **安全与边界**：路径穿越防护复用 `resolveFile`（只取 basename）；fileId 校验 16 位十六进制；分片仅接受请求来源会话（防其他会话注入）；会话断开未完成传输丢弃临时文件，重连后重新请求。
- **清理**：笔记进回收站时引用仍在（恢复后图片可见）；清空回收站后图片文件成为孤儿文件，暂不回收（个人量级可忽略，见开发进度遗留问题）。

## 6. 状态管理设计（Riverpod）

| Provider | 类型 | 职责 |
|----------|------|------|
| `databaseProvider` | Provider<AppDatabase> | 全局数据库单例 |
| `noteRepositoryProvider` | Provider<NoteRepository> | 数据读写统一入口 |
| `notesStreamProvider` | StreamProvider<List<Note>> | 笔记列表（drift 流式查询，自动更新） |
| `searchQueryProvider` | StateProvider<String> | 当前搜索关键字（空串=不过滤） |
| `editorNoteProvider` | FutureProvider<Note?> | 编辑页当前笔记 |
| `discoveryProvider` | StateNotifierProvider | UDP 广播发布/发现的设备列表 |
| `syncConnectionProvider` | StateNotifierProvider | WebSocket 连接状态、已连接设备、最近同步时间 |
| `syncStateProvider` | StateNotifierProvider | 同步进行中标志、错误信息 |
| `deviceIdentityProvider` | Provider<DeviceIdentityStore> | 本机 deviceId/设备名/信任列表（统一入口，见 7.3 节） |
| `syncServiceProvider` | Provider<SyncService> | 同步编排：enable/disable、对端会话、配对队列、冲突事件流（见 7.1/7.3 节） |
| `pairingDialogControllerProvider` | Provider<PairingDialogController> | 全局配对弹窗控制器：订阅 pairingEvents/冲突事件流，rootNavigatorKey 弹窗（task-14） |

**原则**：UI 只读 Provider 渲染，所有变更走 Repository / SyncService 方法；同步事件到达后统一写库，drift 流自动驱动 UI 刷新——**单向数据流**，不手动 setState 同步 UI。

## 7. 同步协议设计

### 7.1 同步拓扑与传输层（v4：P2P 对等 + UDP 广播发现 + 智能扫描/直连优先）

**v2 变更：由主机-客户端改为 P2P 对等模式。** 每台设备既是服务端又是客户端，两两直连；身份与信任基于持久化 deviceId，不依赖 IP。

**v3（task-24）变更：发现层由 mDNS 改为 UDP 广播**（参考 Syncthing lib/discover/local.go 的周期广播 + LocalSend multicast_discovery.dart 的上线三连发与回播机制），连接/同步层零改动。UDP 广播不依赖 mDNS/Bonjour：无 MulticastLock、无 NSBonjourServices 要求、跨平台行为一致；代价是**协议不兼容旧版**——所有设备需升级到新版，旧版（mDNS）与新版（UDP）互不可见（见 README「发现机制升级说明」）。

**v5（task-31）变更：互联手动化 + 保活重构。** 见本节下文「task-31 互联手动化」与「保活」小节。

**v4（task-27）变更：发现侧改为按需扫描 + 直连优先（用户确认方案）。** 通告（发布侧）保留：每台设备在 UDP 广播端口 **58888**（与 WebSocket TCP 端口同号，UDP/TCP 独立协议栈不冲突）周期广播 JSON 通告；扫描（发现侧）**常态不主动扫描**——不长期占用监听 socket，仅在以下时机按需扫描：

- **手动扫描（task-31 互联手动化）**：同步页「扫描设备」按钮 → [SyncService.scanOnce(window)] → [DiscoveryService.scanOnce]（绑定 UDP 58888 收集 **30s** 窗口后停止，列表**定格**——两次扫描之间列表不更新、不自动清空，下次扫描按 [deviceExpiry] 清理超时设备）；未配对设备**不自动扫描**，仅手动扫描后可见；
- **退避扫描（task-31 已删除）**：原「已配对断线退避扫描」（5s→…→60s 封顶持续低频扫描）已随互联手动化删除——直连失败静默结束，等对方凭缓存直连本机或用户手动扫描。

**广播（发布侧，保留）**：
  - **协议格式**：UTF-8 编码的 JSON `{v:4, deviceId, name, port, ts}`（v=协议版本，task-30 图片同步升至 4，与 hello 携带的协议版本一致；接收端忽略不兼容版本；deviceId=持久化身份；name=设备名；port=WebSocket 监听端口；ts=发送时刻 epoch ms）。对端 IP 由**数据报源地址**获得（协议不含地址字段）。
  - **发送（逐网卡广播 + 兜底）**：枚举 IPv4 网卡（过滤虚拟/断开网卡，排除 loopback/链路本地），按「IP+掩码」推导各网卡子网广播地址（dart:io 的 NetworkInterface 不暴露 netmask，按私有网段惯例推导：`10/8`、`172.16/12`、`192.168/24`，其余按 `/24` 默认）+ **`255.255.255.255` 兜底**；发送失败容忍（try-catch + 日志，不影响后续通告）。
  - **发送时序（上线三连发 + 周期通告）**：`publish` 时按**可注入延迟**（默认 100ms/500ms/2s）连发三次（LocalSend 式上线宣告，广播丢包容忍）；随后按**可配置间隔**（默认 30s）周期通告（Syncthing 式）；无显式 goodbye——下线凭离线判定（扫描结束按 [deviceExpiry] 清理）。
  - **新设备回播（LocalSend 式握手）**：扫描窗口内收到**新 deviceId** 的通告后**立即回播一次**自己的通告（双方互相知晓）；防已收到风暴：记录最近回播的 deviceId+时间，回播后**限频窗口**（默认 30s）内不再对同一设备回播。
  - **接收与离线判定（扫描窗口内）**：绑定 UDP 58888（reuseAddress；macOS/Linux 加 reusePort 支持同机多实例/多进程共存，Windows 不支持 SO_REUSEPORT 降级为仅 reuseAddress——Windows 下 SO_REUSEADDR 允许多 socket 同端口且广播投递给全部 socket）监听 anyIPv4；JSON 解析容错（坏包忽略）；按 **deviceId 去重**（同名设备/多网卡不合并）；isSelf = 通告 deviceId == 本机 deviceId（过滤自己，广播会回环）；按 deviceId 记录 lastSeen，每次扫描结束清理超过**可配置窗口**（默认 90s）无通告的设备（列表定格期间不清除）。
  - **平台适配**：发送 socket 显式开启 `SO_BROADCAST`（RawDatagramSocket.broadcastEnabled）；Windows 无 reusePort；Android 的 WiFi 省电只过滤**多播**包，**广播**不受 MulticastLock 限制（task-24 移除 CHANGE_WIFI_MULTICAST_STATE 权限与原生 MethodChannel）；iOS 仍需 `NSLocalNetworkUsageDescription`（本地网络权限弹窗）+ `NSAppTransportSecurity/NSAllowsLocalNetworking`（ws:// 明文意图声明）；`NSBonjourServices` 已删除（UDP 广播不需要 mDNS 声明）；macOS 沙盒仍需 network.server/client Entitlements。
- **连接**：`ws://<对端当前IP>:<固定端口>`（默认 58888，可配置）；**连接去重**：deviceId 字典序小者主动发起连接，大者只监听接受，保证每对设备仅一条连接
- **连接策略（task-31 重连责任转移）**：打开同步开关 / enable 后，只开 WebSocket 服务端等待已配对设备凭缓存直连本机，同时本机也对全部「应主动连接」的已配对设备（autoConnect && 非手动断开）凭**地址缓存**抢连（抢占式，task-30 迭代：不再按 deviceId 大小分配发起权——双方同时抢连由会话去重 [_registerPeerId]/[_shouldReplace] 保证每对仅一条连接）；直连失败**静默结束**（不自动扫描、不自动重连），等对方上线连本机或用户手动「扫描设备」。地址缓存持久化到设置表（`peer_addr_<deviceId>` → `ip:port`，连接建立/发现时刷新，跨重启有效）
- **自动连接（task-16 WiFi 式 + task-31 互联手动化）**：打开同步开关 → 只凭缓存直连已配对设备（无缓存/失败静默，不扫描）；已配对设备**上线方**主动连回（重连责任在重新上线方，不在在线方）；未配对设备需用户手动「可被发现」+ 对方「扫描设备」+ 点击 + 对方同意（见 7.3 认证流程）。自动连接条件：**已配对 && 该设备 `autoConnect=true` && 非手动断开**
- **手动连接开关（task-31）**：设备行「手动连接」开关（上）——打开 = 手动连接该已配对设备（清除手动断开标记 + 凭缓存直连，[SyncService.connectTrustedPeer]）；关闭 = 断开（会话级手动断开标记，当下不自动重连）。连接后开关自动打开（值 = 连接中/连接意愿）
- **手动断开（task-16，WiFi 式）**：设备行「手动连接」开关关闭后，该设备进入**会话级手动断开状态**（按对端 deviceId 记录于内存 `_manuallyDisconnected`，不持久化）——自动连接逻辑**跳过**该设备，当下不自动重连；**重新开启同步（disable/enable）或重启 App 时标记清除**（按 autoConnect 重置，符合「自动开+手动关→下次启动自动打开并连接」）；**手动连接该设备（手动连接开关打开）时清除标记**
- **每设备「自动连接」配置（task-16，WiFi 式；task-32 修订语义）**：`TrustedDevices` 表 `autoConnect` 字段（默认 true，drift schema v2→v3 迁移）。**只管本机是否自动发起连接**——关闭后本机不自动连该设备（保持配对），但**不控制是否接受对方连接**：已配对设备的连接（无论自动/手动发起）一律无条件接受；两端开关独立、不同步
- **task-31 互联手动化**：enable 只开 WebSocket 服务端（**不持续 UDP 广播**）。向外广播由同步页「可被发现」按钮触发 [SyncService.announceTemporarily]——临时广播 **30s**、每 **5s** 一次，到点自动停止；「扫描设备」触发 30s 扫描窗口。新设备配对 = 一方「可被发现」+ 另一方「扫描设备」
- **自动连接语义（task-32 修订，Q4 拒绝已移除）**：autoConnect 只管本机是否自动发起连接，**无拒绝机制**——已配对连接无条件接受。旧版 [AutoConnectRejectedMessage] 接收处理保留为内存标记（本次运行不再自动尝试，不持久化、不影响手动连接），仅兼容旧对端
- **保活（task-31 会话层唯一机制）**：传输层 15s ping 已删（消除双 ping）。会话层每 **2s** 发送 `{type:"ping"}`，**任何入站消息（含 ping/pong）即保活证据**，连续 **5s** 无入站判定失联 → 关闭会话。在线方不主动重连（重连责任在重新上线方：重新上线方 enable 后凭缓存直连回在线方）
- **重连（task-31 重连责任转移）**：断线后**在线方不主动重连**（不自动退避重连、不退避扫描）；重新上线方（enable / 回前台）凭地址缓存直连回在线方（[retryConnections]/[_runDirectConnectPhase]）；地址缓存换 IP 后失效时，手动「扫描设备」发现新地址 → 更新缓存 → 直连

### 7.2 消息协议（JSON）

| 消息 | 方向 | 载荷 | 说明 |
|------|------|------|------|
| `hello` | 双向 | `{deviceId, deviceName}` | 连接建立后身份声明（双方互发） |
| `welcome` | 双向 | `{deviceId, deviceName, trusted}` | 身份确认；trusted=true 表示对端在本地信任列表 |
| `pairing_request` | 双向 | `{deviceId, deviceName}` | 发起配对请求（请求对方同意连接） |
| `pairing_accept` | 双向 | `{deviceId, deviceName, secret}` | 对方同意：携带本机生成的验证密钥（验证方密钥），双方写信任列表 |
| `pairing_fail` | 双向 | `{reason}` | 拒绝/失败 |
| `unpair` | 双向 | `{deviceId}` | 取消配对通知：双边同时解除信任并断开 |
| `auto_connect_rejected` | 双向 | `{deviceId}` | 自动连接被拒绝通知（task-31，task-32 起仅兼容旧对端）：新版本不再主动发送（无拒绝机制）；旧对端发送时接收方记内存标记（本次运行不再自动尝试，不持久化） |
| `challenge` | 双向 | `{nonce}` | 握手认证挑战（HMAC） |
| `challenge_response` | 双向 | `{nonce, hmac}` | 对端用本机密钥计算 HMAC 响应 |
| `sync_request` | 双向 | `{}` | 请求全量同步（连接建立 / 手动同步时） |
| `sync_data` | 双向 | `{notes: Note[]（含回收站条目）, tombstones: Tombstone[], folders: Folder[]（含软删除条目，task-32 v6）}` | 对端全量快照：先合并墓碑再合并笔记与文件夹（LWW 各自裁决）；`tombstones`/`folders` 缺省空列表，兼容旧对端解析 |
| `note_upsert` | 双向 | `{note: Note}` | 增/改/软删除/恢复推送——deletedAt 非空即软删除（回收站）、null 即恢复，携带完整 version |
| `folder_upsert` | 双向 | `{folder: Folder, origin}` | 文件夹增/改/软删除/置顶/排序推送（task-32 v6）——deletedAt 非空即删除（文件夹删除不可恢复）；origin 语义同 note_upsert（v5 起） |
| `note_delete` | 双向 | `{id, version, deletedAt?}` | 清空（物理删除）推送；`deletedAt`（删除时刻，可选，task-21 新增）供同 version 时间裁决，旧对端不带时退化为同 version 删除优先；对端校验后物理删除 + 写墓碑 |
| `devices_update` | 双向 | `{devices: DeviceInfo[]}` | 已连接设备列表变更广播 |
| `file_request` | 双向 | `{fileId, expectedSize?, ext?}` | 附件请求（图片同步 v4，task-30；ext 为原图方案修订）：接收方发现缺失附件（`attachments/<fileId>.<ext>`）时向来源会话发送；`expectedSize` 为期望字节数（接收方通常未知，null=不限），`ext` 为期望扩展名（沿用正则捕获，null=旧对端/未知，发送方扫描目录匹配 hash.* 兜底），发送方校验本地文件存在且大小一致才响应 |
| `file_chunk` | 双向 | `{fileId, chunkIndex, totalChunks, data}` | 附件分片（图片同步 v4）：发送方按 64KB 分片逐片发送，`data` 为分片字节 base64 编码；WebSocket 保序，接收方按序追加写入 `.part` 临时文件 |
| `file_complete` | 双向 | `{fileId}` | 附件传输完成（图片同步 v4）：接收方触发 `AttachmentsStore.finalize`——校验 sha256 前 16 位 == fileId 后重命名落盘，失败丢弃临时文件可重新请求 |

**Note JSON 载荷**（task-28 修订，task-29 再修订，task-32 v6 加 folderId）：`note_upsert` / `sync_data` 中的 Note 统一携带 `{id, title, content, createdAt, updatedAt, version, deletedAt, isPinned, tags, folderId}`——`folderId`（字符串，所属文件夹，null/缺失 = 未分类，task-32 v6）随笔记 upsert 全量同步（LWW 合并规则不变）；旧对端/旧数据缺失该字段时按 `null`（未分类）处理，向后兼容。**`content` 自协议 v3（task-29 富文本）起为 delta JSON 字符串**（Quill Document 序列化）；LWW 合并把 content 当不透明字符串处理（格式由协议版本保证）。**协议 v4（task-30 图片同步）**：content 格式不变，新增 file_request/file_chunk/file_complete 消息传输附件二进制（见上表与 3.4 节）；**v3 及以下对端（无图片同步协议）不互连**——hello 协议版本 < 4 时回 pairing_fail{reason:'协议版本不兼容，请升级应用'} 后断开（全员升级，见 README）。存量纯文本在 schemaVersion 7→8 迁移时转换为 delta；列表摘要/字数经 `Note.plainTextOf` 提取纯文本。

**Folder JSON 载荷**（task-32 v6）：`folder_upsert` / `sync_data` 中的 Folder 携带 `{id, name, createdAt, updatedAt, version, deletedAt, isPinned, sortOrder, origin}`——字段与 folders 表一致；置顶/排序/重命名/软删除均走 `folder_upsert`（携带完整文件夹），对端按 LWW 合并规则采用/丢弃（无墓碑，软删除语义）。全量同步双向对齐：本机全部文件夹（含软删除）随 `sync_data` 下发并以 `folder_upsert` 回推对端；fan-out 转发门控与笔记一致（仅实际变更时转发，v6 沿用）。

**Tombstone 载荷**（task-21 新增，随 `sync_data` 交换）：`{id, version, deletedAt}`——被清空笔记的 id、删除时刻 version、物理删除时刻（epoch ms）。协议层独立定义（sync_protocol.dart），与数据层 drift `Tombstone` 字段同构，SyncService 组装/解析时互相转换；墓碑**永不清除**，全量快照携带全部墓碑供对端防复活拦截。

**全量同步为双向对齐**（task-9 联调补充，task-21 扩展墓碑交换）：客户端收到 `sync_data` 合并对端快照后，把本机全部笔记以 `note_upsert` 回推对端（LWW 合并，幂等、不经 changes 通道无回声），并把本机墓碑以 `note_delete` 回推（携带 deletedAt，对端按 7.4 统一比较器物理删除旧数据/补墓碑）。保证客户端离线期间新建/修改/清空的笔记都能到达对端（F8「双向数据一致」、验收标准 4「重连后数据对齐无丢失」）。

**多客户端 fan-out 转发**（task-10 补充，task-12 收紧为仅已配对，**task-15 修订为仅实际变更时转发**）：3 台及以上设备（P2P 全互联 mesh）场景下，任一设备收到对端的 `note_upsert` / `note_delete`，本地 LWW 合并后**仅当合并实际变更本地**（`mergeRemoteNote` / `mergeRemoteDelete` 返回 true）才向除来源会话外的**所有已就绪（信任）对端**转发原消息；未变更（重复/回声）消息**直接丢弃**。task-15 修订原因：全互联 mesh 下无条件转发会让未变更的回声消息被继续中继——A 的变更经 B→C→A→B…无限循环（消息风暴，联调实测 1.5s 内单条笔记被每台设备处理数千次）。改为仅实际变更时转发后，每条笔记在 mesh 中至多被每台设备处理 2 次（1 次直接推送 + 1 次对端 fan-out，第二次为未变更回声被丢弃），消息链收敛（verify_sync.dart 场景十一断言每台 ≤ 2 次且计数停止增长）。task-21：软删除/恢复（note_upsert，deletedAt 非空/为空）与清空（note_delete）三类操作同样受该门控约束（verify_sync.dart 场景十一覆盖三种操作）。防回声：远端数据写库走 `mergeRemoteNote` / `mergeRemoteDelete` / `mergeRemoteTombstone`（不经 changes 通道，见 note_repository.dart 类注释约定），不会回推；删除消息转发时携带原始 version（task-21 起含 deletedAt），防乱序/时间裁决语义不变。

### 7.3 认证与配对流程（v4：请求-同意 + HMAC 挑战认证）

**配对（首次连接，无密码，用户确认方案）**：
```
A 点选发现列表中的 B → 发 pairing_request{deviceId, name}
B 收到 → 全局弹窗「xx 请求连接」→ 用户点「同意」：
  → B 生成随机密钥 K（32 字节）→ 存入信任列表（A 的条目）→ 发 pairing_accept{deviceId, name, secret: K}
  → A 将 K 存入信任列表（B 的条目）→ 确认回发同一密钥（pairing_accept，载荷不变）
  → B 幂等刷新 → 双方配对完成（每对设备共享一个密钥）
用户点「拒绝」→ 发 pairing_fail → 请求方提示被拒绝并断开
```
> **实现要点（task-27 修订）**：方案原描述为「双方各生成一个密钥（K_B 验证 A、K_A 验证 B）交换」，但单 `secret` 列约束下挑战握手要求**验证方持有的密钥 == 应答方持有的密钥**（见下方握手流程）——故实际实现为**每对设备单一共享密钥**：接受方生成并随 pairing_accept 发送，请求方存库后确认回发同一密钥，双方以同一密钥完成双向 HMAC 验证。这是对「双密钥交换」的安全性等价格简（熵 256 位不变，单向泄露即需重新配对，与双密钥语义一致）。

**每次连接握手（HMAC 挑战认证，防伪装 deviceId）**：
```
连接建立 → 发起方发 hello{deviceId, deviceName, protocolVersion:2}
接受方查信任列表：
  命中且持有密钥 → 发 challenge{nonce（随机 32 字节）}
    → 对端用本地存的该设备密钥计算 HMAC-SHA256(secret, nonce) → challenge_response{nonce, hmac}
    → 验证方比对 hmac：匹配 = 真身（持有配对时交换的密钥）→ welcome{trusted:true}
      不匹配/无密钥 → welcome{trusted:false} → 按未配对处理（发起方发 pairing_request）
  未命中 → welcome{trusted:false} → 发起方发 pairing_request
发起方收到 welcome{trusted:true}（接受方已验证明发方真身）→ 反向 challenge 对端证明其真身
  （防伪造 welcome 骗取信任——伪装者不知道密钥，无法应答）→ 验证通过 → 进入同步流程
```
> 挑战超时兜底：发出 challenge 后 10s 无响应按未配对处理（防会话卡死）。协议版本：hello 携带版本 v4（通告 `v` 字段同值，task-30 图片同步升级）；对端 hello 版本 < 4（v3 及以下旧协议）→ 回 pairing_fail{reason:'协议版本不兼容，请升级应用'} 后断开——**不互连**，需全员升级（见 README）。

**取消配对（双边解除，不残留）**：任一方取消 → 发 unpair{deviceId} → 对端移除信任 + 断开；本机同步移除信任与地址缓存。**实现要点（task-27）**：密钥为 32 字节随机（`crypto` 包 HMAC-SHA256，无第三方依赖）；信任列表 `trusted_devices` 表加 `secret` 字段（schemaVersion 4→5 迁移；v3 旧配对升级后 secret=null——升级后首次连接按未配对处理，需重新走请求-同意配对获得密钥）；配对请求在 SyncService 内 FIFO 队列排队，UI 由全局配对弹窗消费（rootNavigatorKey，任意页面可见，v4 改「同意/拒绝」按钮，无密码输入）；`_pairingRole`（requester/consenter）角色守卫保留（仅接受自己发过请求/收到过请求的配对确认，防单方面伪造）；设备 ID 冲突防护语义不变（见下文）。

**设备 ID 冲突防护（task-14 新增，用户需求）**：

- **握手/会话登记**：连接建立后对端 `hello`/`welcome`/`pairing_request`/`pairing_accept` 声明的 deviceId 与本机相同（常见于从备份恢复数据导致两台设备身份相同）→ 拒绝该连接并断开，同时发出 `DeviceIdConflictEvent`（`deviceIdConflictEvents` 流），UI 提示「设备 ID 冲突：检测到与本机相同的设备 ID（可能恢复了备份数据），请在设置中重置设备 ID」。
- **发现列表**：UDP 广播发现到与本机相同 deviceId 的设备 → 不自动连接（即使信任列表含同 ID）+ 上报冲突事件；同一冲突设备持续在发现列表只报一次（去重，避免周期通告刷屏），从列表消失后再出现可重新上报。
- **不误报**：发现与本地信任列表相同 deviceId 但不同 IP 的设备属正常（IP 变化），不报警——仅对与本机相同的 ID 报警。
- **手动连接**：用户点击同 ID 设备发起连接 → 被拒（连接不建立）+ 冲突事件。
- **重置设备 ID**：设置弹窗提供「重置设备 ID」入口——重新生成 deviceId 并清空信任列表（旧配对关系失效需重新配对），断开全部会话并以新身份重新发布 UDP 通告（`SyncService.resetDeviceIdentity` → `DeviceIdentityStore.resetDeviceId`）。这是冲突修复的标准操作：重置其中一台的 ID 后，两台设备身份不同即可正常配对。

**信任列表**：持久化存储（deviceId + 设备名 + 首次配对时间 + `autoConnect` 自动连接开关（task-16，默认 true）+ **`secret` HMAC 认证密钥**（v4，每对设备共享一个）。凭据是 deviceId，IP 变化不影响。**取消配对（v4 双边解除）**：同步页「取消配对」→ `SyncService.unpairPeer(deviceId)` = 发 unpair + 断开连接 + 移除信任列表 + 清除地址缓存/手动断开标记 + 广播状态更新；**双边生效**（对端收到 unpair 同步移除信任并断开，不残留），取消后重新连接需重新请求配对。

### 7.4 合并流程

> **task-21 修订（v3 统一比较器落地）**：对所有操作（note_upsert / note_delete /
> sync_data 中的笔记与墓碑）统一按同一比较器裁决：**version 大者胜 → 相等比操作
> 时间（软删条目以 deletedAt 计、正常条目以 updatedAt 计）→ 平局删除优先**；
> 墓碑按同一比较器拦截过期数据（墓碑 version ≥ 消息 version 且操作时间不更新 →
> 拒绝防复活；消息 version > 墓碑 version，或同 version 操作时间更新 → 允许复活）。

```
收到 sync_data / note_upsert：
  0. 墓碑拦截：该 id 有墓碑时，仅当远端 version > 墓碑 version，或 version 相等
     且远端操作时间 > 墓碑删除时间才放行（防复活，见 mergeRemoteNote）
  1. 按 id 查本地笔记
  2. 本地不存在 → 直接插入（保留远端 version / deletedAt）
  3. 本地存在 → 比较 version：
     - 远端 version > 本地 → 采用远端
     - 远端 version < 本地 → 忽略（保留本地）
     - 相等 → 比较操作时间（updatedAt vs deletedAt），新者胜；本地胜时无需动作
  4. 采用远端时 version 取 max(本地, 远端)，保证本地 version 单调递增（禁止回退）
  5. 标题与正文与本地一致时仅对齐版本/时间戳，不重写内容

收到 sync_data 墓碑列表（先于笔记处理，见 _onSyncData）：
  1. mergeRemoteTombstone：写/提升本地墓碑（version 只增不减，永不清除）
  2. 拦截被墓碑覆盖的本地旧数据：本地笔记 version < 墓碑 version，或 version
     相等且操作时间 ≤ 墓碑删除时间（平局删除优先）→ 物理删除本地笔记

收到 note_delete（清空推送，id + version + 可选 deletedAt）：
  1. 本地 version > 消息 version → 忽略（乱序过期）
  2. 同 version 且消息携带 deletedAt → 本地操作时间更新则保留（离线修改复活）
  3. 否则物理删除 + 写墓碑（version 取 max(本地墓碑, 消息 version)，deletedAt
     沿用消息值）；旧对端 note_delete 无 deletedAt → 同 version 删除优先（旧语义）
```

> **task-15 补充**：`mergeRemoteNote` / `mergeRemoteDelete` 返回**是否实际变更本地**
> （写库为 true；未采用远端/内容版本均已一致/本地已删/乱序过期为 false）。
> SyncService 转发（fan-out）仅在实际变更时进行，未变更消息直接丢弃——
> 全互联 mesh 下消息链因此收敛（见 7.2 节 fan-out 规则修订）。
> task-21：软删除/恢复（note_upsert）与清空（note_delete）三类操作均走该门控，
> mergeRemoteTombstone（sync_data 墓碑合并）仅在全量快照内调用、不参与转发。

> **task-9 修订（重要）**：采用远端时 version 取 `max` 而非 `max+1`。原 `max+1` 规则
> 导致接收方版本膨胀，实测会破坏删除防乱序——客户端合并主机更新后 version 高于主机，
> 主机随后发出的 `note_delete`（携带主机侧较低 version）被客户端误判为乱序过期而拒绝，
> 删除无法同步。改为 `max` 后：单调递增不变量保持、删除可正确传播、双向全量对齐后
> 两端版本稳定收敛（无“同步→+1→回推→再+1”版本乒乓）。
>
> 删除防乱序：`note_delete` 携带删除方 version，仅当本地 version ≤ 消息 version 时执行删除
> （本地有更新的修改则保留，乱序删除消息过期作废）。

### 7.4 冲突处理示例

- 设备 A、B 同时编辑笔记 X（version=5）
- A 保存 → version=6；B 保存 → version=6
- A→B 同步：A(6) 与 B(6) version 相等，比较 updatedAt，晚保存者胜
- 输方接收胜方数据并置 version=6（max，不 +1），后续同步全局一致且版本稳定

## 10. 关键决策记录

| 决策 | 选项 | 选择 | 理由 |
|------|------|------|------|
| 同步拓扑 | 主机-客户端 / P2P 对等 | P2P 对等（v2 修订，用户真机实测后变更） | 不分主机客户端、两两直连、任一方变更广播所有对端；连接去重：deviceId 小者主动连接 |
| 首次连接认证 | 无认证 / 设备密码 / 请求-同意 + HMAC | 请求-同意 + HMAC 挑战认证（v4，用户确认） | 首次手动点设备 + 对方同意（无密码），配对时交换随机密钥，每次连接握手 HMAC 验证真身防伪装；配对后永久信任自动连接；身份凭 deviceId 不依赖 IP |
| 同步模块独立性 | 与笔记功能耦合 / 独立可对接 | 独立可对接（用户要求） | 同步引擎（协议+连接+合并）与笔记数据层解耦：外部笔记软件实现同一套数据接口（增删改+merge 入口+变更事件）即可复用同步能力；本项目笔记仅保持基础功能 |
| 冲突策略 | CRDT / LWW | LWW | 个人单写者场景冲突概率极低，LWW 实现简单且足够 |
| 删除策略 | 软删除 / 硬删除+广播 | 硬删除+广播 | 避免墓碑清理复杂度，广播携带 version 防乱序 |
| 状态管理 | Provider / Riverpod / Bloc | Riverpod | 类型安全 + 易测试，社区主流 |
| 路由 | Navigator / go_router | go_router | 官方推荐，配置集中、支持深链 |
| 保活机制 | 传输层 15s ping + 会话层 2s ping / 仅会话层 2s ping | 仅会话层 2s ping（task-31） | 消除双 ping 冗余；入站消息（含 ping/pong）即保活证据，5s 无入站判定失联；日志无 tick 刷屏 |
| 断线重连 | 指数退避自动重连 + 退避扫描 / 在线方不重连、重新上线方凭缓存直连 | 在线方不主动重连（task-31） | 个人设备少、重连责任清晰；重新上线方 enable 后凭 IP 缓存直连回在线方，无重连风暴 |
| 向外广播 | enable 持续周期广播 / 仅手动「可被发现」临时广播 30s | 手动临时广播（task-31，用户确认） | 基本就自己的设备，手动最稳妥；enable 只开 WebSocket 服务端 + 凭缓存直连已配对设备 |
| 设备互联 | 自动发现自动连 / 手动「可被发现」+「扫描设备」 | 手动互联（task-31，用户确认） | 场景少，手动最稳妥；新设备配对 = 一方可被发现 + 另一方扫描设备 |
| 连接状态持久化 | JSON 存 DeviceSettings / 现有 TrustedDevices.autoConnect 列 | 现有列（task-31，用户确认避免过度设计） | 手动连接态是会话级内存态（enable 时清除，符合「下次启动按 autoConnect 重置」）；autoConnect 本就持久化，无需新存储 |
| 每设备连接模型 | 单开关 / 双开关（手动连接+自动连接） | 双开关垂直排列（task-31，用户确认） | 手动连接=当前连接意愿（连接后自动开、手动关=断开、手动开=重连）；自动连接=上线自动连 + 在线方拒绝对方连（Q4） |
| 被拒方向同步 | 被拒方保持开启 / 被拒方自动关闭 autoConnect | 自动关闭并持久化（task-31，用户确认） | 在线方对 autoConnect=false 设备拒绝连接；被拒方收到 auto_connect_rejected 后自动关自己的 autoConnect，避免反复连接被拒 |
| 文件夹归类 | 不做 / 独立表 + folderId 列 | 独立 Folders 表 + notes.folderId 可空列（task-32，用户确认） | 字段体系与笔记同构（LWW 全复用）；folderId null = 未分类；文件夹删除 = 软删除不可恢复（无回收站）；排序 = isPinned DESC → sortOrder ASC（置顶区/普通区各自拖拽排序，跨区走菜单） |
